## Device-independent capture format reconciliation

November 15, 2026 logs showed hardware input at 24 kHz while the cached input-node
output/tap format remained 48 kHz. Beta 17's nil tap negotiation still failed with
`-10868`: the installed app stayed open, but capture failed. Exception containment
was not capture success. This release addresses format negotiation generally,
not a device-name, device A/B/C or AirPods special case.

After the start cue, a fresh hardware format is explicitly supplied to tap
installation. The exception-contained Objective-C adapter reconciles an unconnected
input-node output to that format. Exception-contained output inspection validates
hardware/output/tap/converter agreement before prepare, before start and after
start. Invalid or changing formats fail closed rather than forcing a fallback rate.

Selected device UID validation, cancellation, pre-start observer registration,
locked invalidation, disabled PCM delivery until startup commit and generation-bound
drain/teardown remain preserved. No automatic retries, silent device fallback,
fallback-rate writes, usage-statistics changes or privacy changes are introduced.

## Evidence and its limits

The primary reports user-approved diagnostics using their own permission-owning
scratch app, **not an installed-app replacement**. These are distinct scenarios:

- The production Objective-C adapter's first Bluetooth hardware attempt observed
  actual hardware 24 kHz / output 48 kHz, corrected output to 24 kHz, installed the
  24 kHz tap and succeeded: 15 callbacks, 36,000 frames, then stopped and disposed.
- A second adapter attempt passed start, but a watchdog killed it before graceful
  cleanup. That attempt is **not a pass**.
- One full production Swift `AudioCapture`/`CaptureStartup` attempt with the observer
  enabled passed startup commit: 16 sink callbacks, 24,000 converted frames over
  1.5 seconds, healthyStop true, isRecording false, device-running 0 and normal
  exit. Metadata was 48/48 before initialization and 24/24 after stop; this does
  **not** prove the full Swift path had exactly 24/48 at tap installation. Do not
  conflate it with the adapter's measured mismatch scenario.

Only Bluetooth transport was independently established; the model name AirPods
was not independently verified. No PCM files or transcription were produced.
The installed app, settings and bundle remained unchanged; the primary reported
installed PID 27303 still in its error state. Scratch capture success does not
establish installed end-to-end dictation, actual OTA, macOS 14 hardware acceptance
or comprehensive cross-device coverage: those remain **unverified**.

Source validation reported before publication: full Node
tests 308 passed, 1 skipped; Rust 90 passed, 3 ignored; frontend build, formatting
and Clippy passed. Joffrey's independent read-only review reported no findings
and an independent capture test passed before the full Swift hardware attempt.
Subsequent metadata activation validation is reported separately by the primary.
